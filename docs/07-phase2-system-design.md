# EXTREMIS Creator Hub — Phase 2: System Design

Covers: JPA entities, Flyway migrations, OpenAPI contract for the MVP
tool endpoints, and the auth/payment/delivery sequence diagrams
required by the technical blueprint and the PRD's Phase 2 handoff.

**Honesty note up front:** two data sets below — the BGMI sensitivity
profiles and the sensitivity-conversion yaw constants — are flagged
**DRAFT / PENDING VERIFICATION**. Per the PRD's own launch-blocker
rule ("do not silently guess constants"), neither ships as `active`
until sourced and signed off. This document builds the *structure* so
that verification is a data task, not a code task.

---

## 1. JPA Entities

**Architectural directive (this revision):** the founder has directed
that the MVP database stay lean — only the entities the 5 MVP tools
actually depend on are migrated and deployed now. Commerce,
subscription, affiliate, and admin entities remain fully designed
below (so Phase 5+ implementation isn't blocked on new design work)
but are **not** included in the initial migration; see §2 for the
revised migration progression.

**UUID generation strategy (reworded per review — corrected #1/#2):**
Hibernate generates UUID values on the application/ORM side using
`@UuidGenerator`, avoiding reliance on PostgreSQL-side UUID generation
functions. This is deliberately stated at that level rather than
promising a specific JDK-internal implementation, since the exact
mechanism is Hibernate-version-dependent and the document shouldn't
assert more than it can guarantee. The practical reason for this
choice: it avoids a Postgres extension dependency — `gen_random_uuid()`
requires either Postgres 13+ (built in) or the `pgcrypto` extension on
older versions, and since the target free-tier Postgres provider
(Neon/Supabase/Railway) is not finalized yet, `@UuidGenerator` keeps ID
generation portable across any Postgres version/provider without a
`CREATE EXTENSION` step.

**Single seeding mechanism (corrected #1 — removes the earlier
inconsistency):** all Flyway seed data that needs application-
generated IDs uses a **versioned Flyway Java migration**
(`BaseJavaMigration`, shown in §2) — not a separate `ApplicationRunner`
component. A Java migration is the more consistent choice because it
stays versioned and ordered alongside the SQL migrations in the same
Flyway history table, whereas an `ApplicationRunner` would run on every
startup outside Flyway's migration tracking and could re-run or
race with migrations in ways that are harder to reason about. This
document uses the Java-migration approach everywhere seed rows need
generated UUIDs — there is no second mechanism.

Package: `com.extremis.hub.domain`. All IDs are `UUID`, generated by
Hibernate 6's native `@UuidGenerator` annotation applied directly on
`@Id` (**corrected per review — REQUIRED 4**: this is Hibernate's own
ID-generation annotation, not JPA's `@GeneratedValue`/`GenerationType`
mechanism, and the two are not combined here — every entity below
shows exactly `@Id @UuidGenerator` and nothing else; the earlier draft
of this document ambiguously suggested both were in play at once,
which the actual code never did). Confirm this against the project's
final Hibernate version when Phase 4 starts (`@UuidGenerator` is a
Hibernate 6.2+ annotation; an older Hibernate/Spring Boot version would
need JPA's `@GeneratedValue(strategy = GenerationType.UUID)` instead —
pick one mechanism for the real project and apply it uniformly, don't
mix). All entities carry `createdAt`/`updatedAt` via a shared
`@MappedSuperclass` (`Auditable`), omitted from each listing below for
brevity. **Timestamp ownership (clarified per review — closes #23):**
Hibernate (`@CreationTimestamp`/`@UpdateTimestamp`) is the single
source of truth for these columns; the SQL `DEFAULT now()` in §2 is
only a safety-net default for rows inserted outside Hibernate (e.g. a
raw-SQL Flyway seed), not a substitute for `@UpdateTimestamp` — a
plain SQL `UPDATE` does **not** get its `updated_at` bumped by the
database default, only Hibernate-managed writes do.

```java
@MappedSuperclass
public abstract class Auditable {
    @CreationTimestamp
    private Instant createdAt;
    @UpdateTimestamp
    private Instant updatedAt;
}
```

### 1.1 User / Profile

**When an `app_user` row is created (added per review — correction #4,
resolves the email-vs-anonymous-usage question):** no `app_user` row
is ever created for an anonymous visitor. Anonymous tool use and
anonymous `GeneratedResult`/`ToolUsage` rows always use `user_id =
NULL` — there is no placeholder or synthetic-email user record created
to "hold a slot" for them. An `app_user` row is first created at the
moment a real, verified identity exists — currently that only happens
when Google OAuth is enabled (Phase 16) and a user completes sign-in,
which is why `email NOT NULL UNIQUE` is safe: by the time a row exists
at all, Google has already supplied a verified email. If another
verified-identity mechanism (e.g. email/password) is added later, it
must supply a real email at row-creation time too — this constraint is
intentionally not relaxed to accommodate a future placeholder-user
pattern.

```java
@Entity
@Table(name = "app_user")
public class User extends Auditable {
    @Id @UuidGenerator
    private UUID id;

    @Column(unique = true, nullable = false)
    private String email;

    // UNIQUE added per review (REQUIRED 3): the auth sequence (§4)
    // upserts by google_subject_id, so the DB must enforce that one
    // Google identity maps to at most one app_user. Nullable + unique
    // is safe in Postgres — multiple NULLs are allowed under a unique
    // constraint, which is exactly what's needed pre-OAuth.
    @Column(unique = true)
    private String googleSubjectId; // nullable until OAuth is enabled

    private Instant deletedAt; // soft delete

    @OneToOne(mappedBy = "user", cascade = CascadeType.ALL)
    private Profile profile;
}

@Entity
public class Profile extends Auditable {
    @Id @UuidGenerator
    private UUID id;

    @OneToOne
    @JoinColumn(name = "user_id", nullable = false, unique = true)
    private User user;

    private String displayName;
    private String avatarUrl;
}
```

### 1.4 BGMI sensitivity data (REVISED per founder decision, post-verification-report)

**Schema change rationale:** the Data Verification Report
(`08-data-verification-report.md` §5-6) found zero evidentiary support
for the original `deviceCategory × playStyle` grid — no reviewed
source segments BGMI sensitivity recommendations that way. The
evidence instead clusters around two different axes: whether the
player uses gyroscope, and which scope/zoom level the setting applies
to (gyroscope and ADS sensitivity are both configured per-scope in the
real game). The founder approved pivoting the model to match the
evidence:

```
GyroscopeUsage (GYRO_ON | GYRO_OFF)
        +
ScopeLevel (NO_SCOPE | RED_DOT | SCOPE_3X | SCOPE_4X_ACOG | SNIPER_SCOPE)
        ↓
one BgmiSensitivityProfile row
        ↓
a RANGE (min/max/starting value), not a single "correct" number,
carrying its own confidence level and source
```

Each row's `recommendedMin`/`recommendedMax`/`recommendedStartingValue`
describes the in-game slider that is actually relevant to that
combination: for `GYRO_ON` rows, the "Gyroscope Sensitivity" slider at
that scope; for `GYRO_OFF` rows, the "ADS Sensitivity" slider at that
scope (with `NO_SCOPE` representing plain "Camera Sensitivity", the
free-look setting that isn't scope-gated). This maps directly onto
BGMI's actual settings screen instead of inventing a blended field, and
lets confidence vary per row instead of forcing uniform precision the
evidence doesn't support (some rows — e.g. `SNIPER_SCOPE`, or any
`GYRO_OFF` row — are expected to carry `INSUFFICIENT_DATA` or `LOW`
confidence rather than being dropped or guessed, per §6 below).

```java
public enum GyroscopeUsage { GYRO_ON, GYRO_OFF }
public enum ScopeLevel { NO_SCOPE, RED_DOT, SCOPE_3X, SCOPE_4X_ACOG, SNIPER_SCOPE }
public enum BgmiConfidenceLevel { HIGH, MEDIUM, LOW, INSUFFICIENT_DATA }

@Entity
@Table(name = "bgmi_sensitivity_profile")
@IdClass(BgmiSensitivityProfileId.class)
public class BgmiSensitivityProfile extends Auditable {
    @Id
    @Enumerated(EnumType.STRING)
    private GyroscopeUsage gyroscopeUsage;

    @Id
    @Enumerated(EnumType.STRING)
    private ScopeLevel scopeLevel;

    private Integer recommendedMin;            // nullable — absent when INSUFFICIENT_DATA
    private Integer recommendedMax;             // nullable
    private Integer recommendedStartingValue;   // nullable

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private BgmiConfidenceLevel confidence;

    private String sourceReference;   // nullable when confidence = INSUFFICIENT_DATA
    private Instant lastVerifiedAt;

    @Column(nullable = false)
    private boolean active = false;   // same activation gate as SensitivityGameProfile
}

public class BgmiSensitivityProfileId implements Serializable {
    private GyroscopeUsage gyroscopeUsage;
    private ScopeLevel scopeLevel;
    // equals/hashCode omitted for brevity
}
```

A row with `confidence = INSUFFICIENT_DATA` and null min/max/starting
values is a valid, expected row — it lets the service return an
honest "not enough evidence yet for this combination" response instead
of omitting the combination silently or fabricating a number.
```

## 2. Flyway Migration Progression (revised — lean MVP schema)

Per the founder's architectural directive, the ~20-entity design in
§1 is **not** deployed as a single migration. The MVP ships only the
tables the 5 tools actually need; everything else is staged for later
migrations, written when that phase actually starts (not pre-written
now, to avoid drift between a speculative migration and the entity
design that eventually implements it):

```
V1 — MVP Core
    app_user, profile, tool, tool_usage, generated_result,
    sensitivity_game_profile, bgmi_sensitivity_profile
V2 — Tool seed data (the 5 Tool rows)
V3 — Verified sensitivity_game_profile rows (ONLY after the Data
     Verification Report, see 08-data-verification-report.md, is
     founder-approved for each game)
V4 — Verified/approved bgmi_sensitivity_profile rows (same approval
     gate, separate migration since the evidence and sign-off process
     differ — see 08-data-verification-report.md §5)
V5+ — Authentication additions (google_subject_id already in V1's
     app_user; any future auth-specific columns/tables land here)
V6+ — Commerce (product_category, product, order, order_item, payment,
     subscription, user_entitlement)
V7+ — Affiliate (affiliate_product, affiliate_click)
V8+ — Admin (admin_user), plus feature_flag, email_event,
     analytics_event as needed by whichever phase first uses them
```

**Explicit Phase-to-migration mapping (added per review — closes #14,
so "Phase 16" and "V5" are never left for a developer to infer are the
same thing):**

| Product roadmap phase (`03-development-roadmap.md`) | Migration |
|---|---|
| Phase 16 — Authentication | V5+ |
| Phase 18 — Affiliate architecture | V7+ |
| Phase 19 — Digital product architecture | V6+ (shares the Commerce bucket with Phase 20) |
| Phase 20 — Payment abstraction | V6+ |
| Phase 21 — Display advertising | *(no dedicated table; ad-slot rendering is frontend-only, gated by a `FeatureFlag` row — V8+)* |
| Phase 22 — Premium entitlements | V6+ (`user_entitlement` ships with Commerce, since entitlements are granted by both purchases and subscriptions) |
| Phase 17 — Admin basics | V8+ |

This mapping is illustrative, not contractual — if a phase's actual
scope shifts by the time it starts, the migration version it lands in
can shift too. The point is that at any given time there is one
current answer to "which migration does Phase N need," written down,
rather than left implicit.

`app_user` and `profile` ship in V1 even though authentication (Phase
16) is deferred, because `GeneratedResult.userId` is nullable and
references `app_user` — the column exists from V1 so anonymous and
future-authenticated results share one table without an
ALTER-TABLE migration later (per the already-approved "anonymous and
future authenticated user model").

-- V2__seed_tools.sql
-- IDs generated by the Spring Boot seeding component (see §1's UUID
-- generation strategy note), not gen_random_uuid(), so this migration
-- has no Postgres-version/extension dependency. Flyway's Java-based
-- migration support (a class implementing JavaMigration) is used here
-- instead of raw SQL specifically because the ids must be app-generated
-- UUIDs, not a database function call.

```java
// V2__seed_tools.java (Flyway Java migration)
public class V2__seed_tools extends BaseJavaMigration {
    @Override
    public void migrate(Context context) throws Exception {
        record Row(String toolType, String slug, String name, String category) {}
        List<Row> rows = List.of(
            new Row("KD_CALCULATOR", "kd-calculator", "KD Ratio Calculator", "competitive"),
            new Row("VALORANT_SENSITIVITY_CONVERTER", "valorant-sensitivity-converter", "Valorant Sensitivity Converter", "competitive"),
            new Row("BGMI_SENSITIVITY_HELPER", "bgmi-sensitivity-helper", "BGMI Sensitivity Helper", "competitive"),
            new Row("TITLE_GENERATOR", "gaming-title-generator", "Gaming YouTube Title Generator", "creator"),
            new Row("DESCRIPTION_GENERATOR", "gaming-description-generator", "Gaming YouTube Description Generator", "creator")
        );
        try (var stmt = context.getConnection().prepareStatement(
                "INSERT INTO tool (id, tool_type, slug, name, category, premium_only) VALUES (?, ?, ?, ?, ?, false)")) {
            for (Row r : rows) {
                stmt.setObject(1, UUID.randomUUID());
                stmt.setString(2, r.toolType());
                stmt.setString(3, r.slug());
                stmt.setString(4, r.name());
                stmt.setString(5, r.category());
                stmt.executeUpdate();
            }
        }
    }
}
```

## 3. OpenAPI Endpoint Contract Skeleton (relabeled per review — REQUIRED 8)

tool-specific schemas are deliberately not re-listed here (the PRD is

## 5.1 Digital Product Delivery — Access Control Detail

- `Product.fileRef` never points to a publicly reachable static path.
- Download links are generated on-demand by the backend as
  short-lived, signed URLs (or a proxied download endpoint gated by
  `UserEntitlement` check) — expiring within a bounded window (e.g. a
  few hours), not permanent links.
- Every download request re-checks the entitlement server-side; a
  leaked link stops working once it expires, even before the
  entitlement itself would.
